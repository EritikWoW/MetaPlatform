## Архітектурні межі

Поточний цільовий шлях доступу такий:

```text
Configurator / Client -> RuntimeGateway -> Runtime -> mpdb
```

Manifest є джерелом істини для структури. Structure cache є лише оптимізацією. Робоча база не повинна відкриватися UI напряму, а імпорт має проходити через `backup -> staging -> validate -> swap`.

## Знайдені ризики

### Високий пріоритет

1. Повний імпорт бізнес-даних із `.1CD` ще не завершений: попередній packed-імпорт містить sample-ліміт і не доводить повноту даних документа «Реалізація товарів і послуг».
2. Повторний імпорт у вже заповнену packed-таблицю потребує захисту від дублювання, коректного reset/rebuild і перевірки row locator.
3. Для частини enumerations та reference-полів потрібне повне відновлення display names і UUID/DBNames-мапінгу.
4. Потрібен окремий end-to-end gate: запуск Runtime, відкриття Configurator, отримання одного об'єкта, відкриття форми та читання реквізитів/табличної частини без зависання.

### Середній пріоритет

1. Холодний старт і закриття UI потрібно перевірити не тільки unit-тестами, а й через реальний процес з timeout та аналізом Runtime log.
2. IDE має розширити diagnostics, definition/reference navigation, completion, signature help, форматування і поведінку двох локалей на реальних імпортованих модулях.
3. Потрібні CI-перевірки для тестів, compileall, імпортного smoke-тесту та перевірки, що приватні дані не потрапили до коміту.
4. Потрібен відтворюваний development/release setup з зафіксованими залежностями та документацією запуску.

## План етапів

Деталізований план створено окремими GitHub Issues з префіксами `[Phase 1]` ... `[Phase 6]`. Кожен issue містить нумерований checklist, критерії приймання та залежності.

Порядок робіт:

1. Надійність Runtime і завершення процесів.
2. Повна міграція бізнес-даних і зв'язування реквізитів.
3. Metadata/Configurator: імена, ієрархія, форми та рухи.
4. IDE: синтаксис, diagnostics, navigation, completion і локалі.
5. Client: повний runtime-backed сценарій бізнес-об'єкта.
6. Release quality: CI, packaging, performance gates і документація.

Issue не вважається виконаним лише через зелені unit-тести: для етапів 1, 2 і 5 обов'язковий representative runtime/UI smoke-test.
